A1 · 파일별 역할과 읽는 순서

개념 정의

컴포넌트는 화면을 구성하는 함수이고, 커스텀 Hook은 상태와 연결 로직을 묶은 함수입니다.

실행 예시

화면을 먼저 읽고, 그 화면이 호출하는 함수로 이동합니다.

코드를 읽는 순서

화면

main.jsx → App.jsx → AuthPanel / TodoPanel

연결

firebase.js → useAuth.js / useTodos.js

서버 규칙·배포

firestore.rules → pages.yml → Nginx 설정

조금 더 자세히

App은 로그인 여부에 따라 화면을 고릅니다. AuthPanel은 인증 요청, TodoPanel은 할 일 입력과 표시를 맡습니다. useAuth와 useTodos는 각각 인증 상태와 문서 변화를 관찰합니다. Rules는 브라우저 밖 Firebase 서버에서 적용됩니다.

문법과 실행 과정을 자세히 읽기

호출 방향

main.jsx가 App을 화면에 올립니다. App은 useAuth()의 반환값으로 화면을 고르고, 로그인했다면 TodoPanel에 uid를 전달합니다. TodoPanel은 useTodos(uid)를 호출해서 목록과 작업 함수를 받습니다. 파일을 읽을 때 import 문에서 다음 파일을 찾으세요.

화면과 연결을 나눈 이유

TodoPanel의 JSX는 무엇을 보여 줄지 결정합니다. useTodos는 어떤 경로를 관찰하고 어떤 요청을 보낼지 결정합니다. 버튼 모양을 바꾸면 컴포넌트, 조회 개수를 바꾸면 Hook을 먼저 살펴보면 됩니다.

실행 위치

React와 Firebase SDK는 사용자 브라우저에서 실행됩니다. firestore.rules는 Firebase 서버가 적용합니다. pages.yml은 GitHub runner가 실행하고, nginx-mini-todo.conf는 Ubuntu의 Nginx가 읽습니다. 모든 파일이 브라우저에서 실행되는 것은 아닙니다.

A2 · JSX와 React의 시작점

개념 정의

JSX는 JavaScript 안에서 화면 구조를 표현하는 문법입니다.

실행 예시

브라우저 진입 → main.jsx 실행 → App 화면 표시

코드를 읽는 순서

시작 위치

HTML의 id="app" 요소를 찾습니다.

render

<App />부터 React 화면을 만듭니다.

StrictMode

개발 중 연결·정리 로직을 추가 점검합니다.

조금 더 자세히

createRoot는 React가 관리할 DOM의 시작점을 정합니다. JSX의 <App />는 App 함수를 통해 만든 컴포넌트를 뜻합니다. StrictMode는 개발 중 Effect의 설정과 정리를 추가 실행할 수 있으므로 관찰을 해제하는 코드가 필요합니다.

문법과 실행 과정을 자세히 읽기

document.getElementById('app')

HTML에서 id가 app인 요소 하나를 찾습니다. 이 요소가 React 화면이 들어갈 자리입니다. HTML의 id와 코드의 문자열이 다르면 올바른 시작 요소를 얻지 못해 화면을 만들 수 없습니다.

createRoot(...).render(...)

createRoot는 그 요소에 React 루트를 만들고, render는 루트에 표시할 JSX를 전달합니다. <App />의 대문자 App은 import한 컴포넌트입니다. <div>처럼 소문자로 쓰는 HTML 태그와 구분하세요.

StrictMode의 범위

개발 모드에서 렌더링과 Effect의 정리를 추가 점검합니다. 개발 중 관찰 시작 로그가 두 번 보인다고 바로 로그인 요청이 두 번 전송됐다고 결론 내리지 마세요. Effect의 관찰 등록과 버튼의 요청 함수를 구분해야 합니다.

src/main.jsx 전체 코드
import { StrictMode } from 'react'
import { createRoot } from 'react-dom/client'
import App from './App.jsx'
import './style.css'

// StrictMode는 개발 중 Effect의 연결·정리가 올바른지 추가로 확인합니다.
createRoot(document.getElementById('app')).render(
  <StrictMode><App /></StrictMode>,
)

공식 문서: https://react.dev/reference/react/StrictMode

A3 · 로그인 여부에 따른 화면 선택

개념 정의

조건부 렌더링은 상태에 따라 표시할 화면을 선택하는 것입니다.

실행 예시

로그인 성공 알림 → user 갱신 → TodoPanel 표시

코드를 읽는 순서

user 있음

로그인한 계정 → TodoPanel

user 없음

로그아웃 상태 → AuthPanel

준비 상태

setupError·ready를 먼저 확인합니다.

조금 더 자세히

user의 초기값이 null이라고 곧바로 로그아웃이라고 판단하지 않습니다. Firebase의 첫 상태 알림을 받기 전에는 ready가 false이므로 확인 중 문구가 보입니다. 설정값 누락은 setupError 화면으로 구분합니다.

문법과 실행 과정을 자세히 읽기

조건 ? 참일 때 : 거짓일 때

삼항 연산자는 조건을 평가해 둘 중 하나의 값을 선택합니다. 여기서는 user가 계정 객체이면 TodoPanel의 JSX를, null이면 AuthPanel의 JSX를 선택합니다. 물음표 뒤와 콜론 뒤를 각각 하나의 화면이라고 읽으세요.

ready를 먼저 확인하는 이유

앱을 처음 열면 user는 null이지만 Firebase가 저장된 로그인 상태를 아직 확인 중일 수 있습니다. ready가 false일 때는 확인 중 화면을 보여 줍니다. 첫 인증 알림을 받은 뒤에 로그인 화면 또는 할 일 화면을 선택합니다.

화면이 바뀌는 계기

AuthPanel이 직접 TodoPanel을 호출하는 것이 아닙니다. 인증 요청 후 onAuthStateChanged의 콜백이 setUser를 호출하고, App이 새 user 값으로 렌더링되면서 선택 결과가 바뀝니다.

import { signOut } from 'firebase/auth'
import { auth, setupError } from './firebase'
import { errorMessage } from './errors'
import { useAuth } from './useAuth'
import AuthPanel from './components/AuthPanel.jsx'
import TodoPanel from './components/TodoPanel.jsx'

export default function App() {
  const { user, ready, message } = useAuth()
  const [leaving, setLeaving] = useState(false)
  const [sessionError, setSessionError] = useState('')

  async function logout() {
    if (leaving) return
    setLeaving(true)
    setSessionError('')
    try { await signOut(auth) }
    catch (error) { setSessionError(errorMessage(error)) }
    finally { setLeaving(false) }
  }

  return (
    <main className="shell">
      <header className="masthead">
        <span>WEEK 07 · MINI TODO</span><span>React + Firebase</span>
      </header>
      <section className="intro">
        <p className="eyebrow">나에게 집중하는 작은 기록</p>
        <h1>나의 작은 할 일</h1>
        <p>오늘 할 일을 저장하고, 끝낸 일에 표시해 보세요.</p>
      </section>
      {setupError ? (
        <section className="panel">
          <h2>Firebase 연결 준비</h2>
          <p>.env.example을 .env.local로 복사한 뒤, Firebase 웹 앱의 설정값 4개를 입력하세요.</p>
          <p>파일을 저장하고 개발 서버를 다시 시작하면 로그인 화면이 나타납니다.</p>
        </section>
      ) : !ready ? (
        <p role="status">로그인 상태를 확인하고 있습니다…</p>
      ) : (
        <>
          {user && <div className="account">
            <span>{user.email}</span>
            <button className="quiet" disabled={leaving} onClick={logout}>로그아웃</button>
          </div>}
          {(message || sessionError) && <p role="alert" className="error">{message || sessionError}</p>}
          {/* [화면] 계정이 바뀌면 key도 바뀌어 이전 목록과 입력 상태를 새로 만듭니다. */}
          {user
            ? <TodoPanel key={user.uid} uid={user.uid} />
            : <AuthPanel />}
        </>
      )}
      <footer>초급프로젝트 7주차 실습 · 사용자마다 자신의 할 일만 볼 수 있습니다.</footer>
    </main>
  )
}

A4 · props로 UID를 전달하고 key로 구분

개념 정의

props는 부모가 자식 컴포넌트에 전달하는 입력값입니다.

실행 예시

A → 로그아웃 → B: A의 입력 상태와 목록을 새로 초기화

코드를 읽는 순서

uid prop

TodoPanel({ uid })에서 전달받습니다.

key

계정이 바뀌면 이전 컴포넌트를 새로 만듭니다.

역할 구분

화면 초기화는 key, 접근 허용은 Rules가 맡습니다.

조금 더 자세히

uid는 Firestore 경로를 만드는 값입니다. key는 React가 컴포넌트의 동일성을 판단할 때 쓰며 일반 prop처럼 자식이 받는 값은 아닙니다. 계정별 화면 구분만으로 보안이 완성되지는 않으므로 Rules도 UID를 검사합니다.

문법과 실행 과정을 자세히 읽기

uid={user.uid}

등호 오른쪽 중괄호 안은 JavaScript 표현식입니다. user.uid가 "ABC"라면 자식 컴포넌트는 uid라는 이름으로 "ABC"를 받습니다. TodoPanel({ uid })의 중괄호는 props 객체에서 uid 속성을 꺼내는 구조 분해 문법입니다.

key={user.uid}

key는 React가 컴포넌트의 동일성을 구분하는 특별한 값입니다. key가 달라지면 이전 인스턴스의 state를 유지하지 않고 새 인스턴스를 만듭니다. 일반 props로 전달되지 않으므로 자식에게 필요한 uid는 별도로 적습니다.

경로 선택과 권한 판정

uid로 users/ABC/todos라는 요청 경로를 만듭니다. 하지만 이 값은 브라우저에서 바꿀 수 있으므로, 서버 Rules가 request.auth.uid와 경로의 uid를 다시 비교해야 합니다.

A5 · useState와 입력값의 연결

개념 정의

state는 React가 렌더링 사이에 기억하는 값입니다.

실행 예시

a 입력 → setEmail("a") → value="a"인 화면

코드를 읽는 순서

email

이번 렌더에서 입력창에 표시할 값

onChange

새 글자를 읽어 setEmail로 전달

다음 렌더

바뀐 state가 value에 반영됩니다.

조금 더 자세히

useState는 현재 값과 값을 변경할 함수를 반환합니다. setEmail을 호출해도 지금 실행 중인 함수의 email 변수가 즉시 바뀌는 것은 아닙니다. 변경은 다음 렌더에 반영됩니다. 입력창의 value와 변경 함수를 함께 연결한 방식을 제어 입력이라고 합니다.

문법과 실행 과정을 자세히 읽기

const [email, setEmail] = useState('')

useState가 반환한 배열의 첫 값을 email, 두 번째 함수를 setEmail이라는 이름으로 꺼냅니다. 빈 문자열은 첫 렌더의 초기값입니다. 이 코드는 렌더 때마다 email을 빈 문자열로 초기화하라는 뜻이 아닙니다.

event => setEmail(event.target.value)

화살표 함수가 입력 이벤트를 받습니다. event.target은 입력 요소이고 value는 입력창의 현재 문자열입니다. 사용자가 abc를 입력하면 setEmail("abc")로 다음 렌더의 상태 갱신을 요청합니다.

value와 onChange를 함께 쓰는 이유

value={email}은 화면을 state에 맞추고, onChange는 사용자 입력을 state로 되돌려 보냅니다. value를 고정하고 변경 핸들러를 빠뜨리면 입력이 의도대로 바뀌지 않습니다. state 변수에 직접 대입하는 대신 setter를 호출해야 React에 변경을 알릴 수 있습니다.

src/components/AuthPanel.jsx 전체 코드
import { useRef, useState } from 'react'
import { createUserWithEmailAndPassword, signInWithEmailAndPassword } from 'firebase/auth'
import { auth } from '../firebase'

A9 · useEffect와 로그인 상태 관찰

개념 정의

Effect는 컴포넌트를 외부 시스템과 연결하고 정리하는 로직입니다.

실행 예시

로그인·로그아웃 알림 → setUser → App 재렌더

코드를 읽는 순서

관찰 시작

onAuthStateChanged가 현재 계정을 알려 줍니다.

상태 반영

user와 ready를 갱신해 화면을 바꿉니다.

정리

return unsubscribe로 관찰을 해제합니다.

조금 더 자세히

콜백은 나중에 상태가 바뀔 때 SDK가 호출할 함수입니다. unsubscribe는 관찰을 끝내는 함수입니다. Effect에서 반환하면 React가 컴포넌트 제거 시 호출합니다. 이 샘플의 빈 의존성 배열 []은 바뀌는 prop/state에 의존하지 않음을 나타냅니다.

문법과 실행 과정을 자세히 읽기

콜백 함수의 실행 시점

currentUser => { ... }를 작성할 때 즉시 그 내용이 실행되는 것이 아닙니다. onAuthStateChanged에 함수를 전달해 두면 SDK가 초기 인증 상태와 이후 변화를 알릴 때 호출합니다. 계정이 없으면 currentUser는 null입니다.

setUser · setMessage · setReady

setUser는 확인한 계정을 저장하고 setMessage는 이전 오류를 비웁니다. setReady(true)는 첫 확인이 끝났다고 알립니다. 오류 콜백도 ready를 true로 만들어 확인 중 화면에 계속 남는 것을 막습니다.

return unsubscribe와 return unsubscribe()

Effect는 정리 함수를 반환해야 합니다. 괄호 없이 반환하면 React가 정리 시점에 호출합니다. 여기서 unsubscribe()를 즉시 호출하면 등록한 관찰이 곧바로 끝납니다. []는 이 Effect가 바뀌는 props나 state를 의존하지 않는다는 표시입니다.

src/useAuth.js 전체 코드
import { useEffect, useState } from 'react'
import { onAuthStateChanged } from 'firebase/auth'
import { auth, setupError } from './firebase'
import { errorMessage } from './errors'

export function useAuth() {
  const [user, setUser] = useState(null)
  const [ready, setReady] = useState(false)
  const [message, setMessage] = useState('')

  // [인증 1] 로그인 상태는 Firebase가 알려주는 현재 계정을 기준으로 합니다.
  useEffect(() => {
    if (setupError) return
    const unsubscribe = onAuthStateChanged(auth, currentUser => {
      setUser(currentUser)
      setMessage('')
      setReady(true)
    }, error => {
      setUser(null)
      setMessage(errorMessage(error))
      setReady(true)
    })
    // [인증 2] 화면 제거 시 관찰을 끝냅니다. StrictMode의 재연결에도 대응합니다.
    return unsubscribe
  }, [])

  return { user, ready, message }
}

A11 · 회원가입과 로그인 요청 선택

await action(...)에서 이 함수의 다음 처리를 기다림

A13 · 연속 클릭을 막는 ref와 busy

개념 정의

ref는 렌더 사이에 값을 보관하며, 바꿔도 자체적으로 재렌더하지 않습니다.

실행 예시

빠른 두 번 클릭 → 진행 중인 요청 동안 추가 호출 차단

코드를 읽는 순서

pending.current

요청 중이면 즉시 false를 반환

busy state

화면의 버튼을 비활성화

finally

성공·실패 모두 잠금을 해제

조금 더 자세히

busy는 UI를 바꾸는 값이고 pending.current는 함수가 바로 확인하는 잠금입니다. run은 action 함수를 받아 실행하고 성공이면 true, 실패면 false를 반환합니다. 네트워크 재시도까지 포함한 서버 수준의 중복 방지 장치는 아닙니다.

문법과 실행 과정을 자세히 읽기

action은 실행할 작업

run(() => addDoc(...))에서 run은 요청을 실행할 함수를 인자로 받습니다. 공통 처리인 중복 클릭 방지, 오류 표시, 잠금 해제를 run에 모으고 실제 생성·수정·삭제 내용만 action으로 바꿉니다.

ref와 state가 함께 필요한 이유

pending.current = true는 같은 실행 흐름에서 즉시 읽을 수 있는 잠금입니다. setBusy(true)는 다음 렌더에서 disabled={busy}에 반영되어 버튼을 잠급니다. ref만 바꾸면 화면이 갱신되지 않고, state만으로는 렌더 전에 들어온 호출을 즉시 막기 어렵습니다.

return 뒤에도 finally 실행

try에서 true 또는 catch에서 false를 반환하려 해도 finally를 먼저 실행합니다. 따라서 성공과 실패 모두 pending과 busy를 해제합니다. finally를 빠뜨려 잠금이 남으면 이후 요청을 계속 차단할 수 있습니다.

src/useTodos.js 전체 코드
import { useEffect, useRef, useState } from 'react'
import { addDoc, collection, deleteDoc, doc, limit, onSnapshot,
  orderBy, query, serverTimestamp, updateDoc } from 'firebase/firestore'
import { db } from './firebase'
import { errorMessage } from './errors'

export function useTodos(uid) {
  const [todos, setTodos] = useState([])
  const [loading, setLoading] = useState(true)
  const [busy, setBusy] = useState(false)
  const [message, setMessage] = useState('')
  const pending = useRef(false)

  // [DB 1] UID가 바뀌면 이전 관찰을 끝내고 새 계정의 목록을 관찰합니다.
  useEffect(() => {
    setTodos([])
    setLoading(true)
    setMessage('')
    const todoCollection = collection(db, 'users', uid, 'todos')
    const todoQuery = query(todoCollection, orderBy('createdAt', 'desc'), limit(50))
    const unsubscribe = onSnapshot(todoQuery, snapshot => {
      setTodos(snapshot.docs.map(item => ({ ...item.data(), id: item.id })))
      setLoading(false)
    }, error => {
      setMessage(errorMessage(error))
      setLoading(false)
    })
    return unsubscribe // [DB 2] 로그아웃으로 화면이 사라질 때도 관찰을 끝냅니다.
  }, [uid])

  function todoCollection() {
    return collection(db, 'users', uid, 'todos')
  }

  // [DB 3] 중복 요청 방지, 오류 표시와 성공 여부 반환을 한곳에서 처리합니다.
  async function run(action) {
    if (pending.current) return false
    pending.current = true
    setBusy(true)
    setMessage('')
    try { await action(); return true }
    catch (error) { setMessage(errorMessage(error)); return false }
    finally { pending.current = false; setBusy(false) }
  }

  function cleanTitle(value) {
    const title = value.trim()
    if (!title || title.length > 80) {
      setMessage('할 일은 공백을 제외해 1~80자로 입력하세요.')
      return null
    }
    return title
  }

  function addTodo(value) {
    const title = cleanTitle(value)
    if (!title) return Promise.resolve(false)
    // [DB 4] ID는 자동 생성하고 생성 시각은 서버가 정합니다.
    return run(() => addDoc(todoCollection(), {
      title, done: false, createdAt: serverTimestamp(),
    }))
  }
  function toggleTodo(todo) {
    return run(() => updateDoc(doc(todoCollection(), todo.id), { done: !todo.done }))
  }
  function renameTodo(todo, value) {
    const title = cleanTitle(value)
    if (!title) return Promise.resolve(false)
    return run(() => updateDoc(doc(todoCollection(), todo.id), { title }))
  }
  function removeTodo(todo) {
    return run(() => deleteDoc(doc(todoCollection(), todo.id)))
  }
  return { todos, loading, busy, message, addTodo, toggleTodo, renameTodo, removeTodo }
}

개념 정의

반환값은 호출한 함수에게 작업 결과를 전달하는 값입니다.

실행 예시

코드를 읽는 순서

제출

새로고침을 막고 현재 title을 전달

성공

addTodo가 true → setTitle('')

실패

false → 입력한 문장을 유지

조금 더 자세히

addTodo는 입력 검사와 DB 요청 결과를 Promise<boolean> 형태로 돌려줍니다. await가 결과를 기다린 다음 if가 판단합니다. 실패 여부와 무관하게 무조건 입력을 지우면 사용자가 다시 작성해야 합니다.

import { useState } from 'react'
import { useTodos } from '../useTodos'

export default function TodoPanel({ uid }) {

    if (window.confirm(`“${todo.title}”을 삭제할까요?`)) await removeTodo(todo)
  }

  return (
    <section className="panel">

      </form>

      <ul className="todo-list">
        {todos.map(todo => (
          <li key={todo.id}>
            {editingId === todo.id ? (
              <form className="edit-form" onSubmit={event => saveEdit(event, todo)}>
                <input value={editedTitle} onChange={event => setEditedTitle(event.target.value)}
                  aria-label="할 일 수정" maxLength={80} required disabled={busy} />
                <button className="primary" disabled={busy}>저장</button>
                <button type="button" className="quiet" disabled={busy} onClick={() => setEditingId(null)}>취소</button>
              </form>
            ) : (
              <>
                <label className={`todo-title${todo.done ? ' completed' : ''}`}>
                  <input type="checkbox" checked={todo.done} disabled={busy} onChange={() => toggleTodo(todo)} />
                  <span>{todo.title}</span>
                </label>

              </>
            )}
          </li>
        ))}
      </ul>
      <p className="hint">최근 생성한 50개까지 표시합니다. 변경 사항은 Firebase에 저장됩니다.</p>
    </section>
  )
}

A17 · UID로 개인 컬렉션 경로 만들기

개념 정의

컬렉션은 문서의 모음이고, 쿼리는 가져올 문서의 조건입니다.

실행 예시

uid가 ABC이면 경로는 users/ABC/todos

코드를 읽는 순서

collection

users / uid / todos 경로를 가리킵니다.

orderBy

createdAt의 내림차순으로 정렬

limit

최근 생성한 50개까지만 가져옵니다.

조금 더 자세히

collection() 호출 자체는 서버에 문서를 생성하지 않습니다. 문서를 추가할 때 실제 데이터가 생깁니다. orderBy(createdAt)는 해당 필드가 있는 문서를 대상으로 하므로 모든 할 일에 생성 시각을 저장합니다. 목록에 없는 오래된 문서가 삭제된 것은 아닙니다.

문법과 실행 과정을 자세히 읽기

경로를 조각으로 읽기

collection(db, "users", uid, "todos")에서 db는 연결 객체입니다. 뒤의 세 인자를 이어 users/ABC/todos처럼 읽습니다. users는 컬렉션, ABC는 사용자 문서 경로, todos는 그 아래 하위 컬렉션입니다.

참조와 조회 조건

collection은 저장 위치를 가리키는 참조를 만듭니다. query는 참조에 정렬·개수 조건을 붙입니다. 이 두 줄만으로 목록을 화면에 가져오지는 않습니다. 다음 onSnapshot이 결과를 관찰합니다.

정렬과 제한의 영향

createdAt이 늦은 문서를 먼저 놓고 그중 50개를 조회합니다. createdAt 필드가 없는 문서는 이 정렬 쿼리의 결과에 포함되지 않습니다. 51번째 문서는 목록에서 빠질 수 있지만 서버에서 삭제된 것은 아닙니다.

import { useEffect, useRef, useState } from 'react'
import { addDoc, collection, deleteDoc, doc, limit, onSnapshot,
  orderBy, query, serverTimestamp, updateDoc } from 'firebase/firestore'
import { db } from './firebase'
import { errorMessage } from './errors'

export function useTodos(uid) {
  const [todos, setTodos] = useState([])
  const [loading, setLoading] = useState(true)
  const [busy, setBusy] = useState(false)
  const [message, setMessage] = useState('')
  const pending = useRef(false)

  // [DB 1] UID가 바뀌면 이전 관찰을 끝내고 새 계정의 목록을 관찰합니다.
  useEffect(() => {
    setTodos([])
    setLoading(true)
    setMessage('')
    const todoCollection = collection(db, 'users', uid, 'todos')
    const todoQuery = query(todoCollection, orderBy('createdAt', 'desc'), limit(50))
    const unsubscribe = onSnapshot(todoQuery, snapshot => {
      setTodos(snapshot.docs.map(item => ({ ...item.data(), id: item.id })))
      setLoading(false)
    }, error => {
      setMessage(errorMessage(error))
      setLoading(false)
    })
    return unsubscribe // [DB 2] 로그아웃으로 화면이 사라질 때도 관찰을 끝냅니다.
  }, [uid])

  function todoCollection() {
    return collection(db, 'users', uid, 'todos')
  }

  // [DB 3] 중복 요청 방지, 오류 표시와 성공 여부 반환을 한곳에서 처리합니다.
  async function run(action) {
    if (pending.current) return false
    pending.current = true
    setBusy(true)
    setMessage('')
    try { await action(); return true }
    catch (error) { setMessage(errorMessage(error)); return false }
    finally { pending.current = false; setBusy(false) }
  }

  function cleanTitle(value) {
    const title = value.trim()
    if (!title || title.length > 80) {
      setMessage('할 일은 공백을 제외해 1~80자로 입력하세요.')
      return null
    }
    return title
  }

  function addTodo(value) {
    const title = cleanTitle(value)
    if (!title) return Promise.resolve(false)
    // [DB 4] ID는 자동 생성하고 생성 시각은 서버가 정합니다.
    return run(() => addDoc(todoCollection(), {
      title, done: false, createdAt: serverTimestamp(),
    }))
  }
  function toggleTodo(todo) {
    return run(() => updateDoc(doc(todoCollection(), todo.id), { done: !todo.done }))
  }
  function renameTodo(todo, value) {
    const title = cleanTitle(value)
    if (!title) return Promise.resolve(false)
    return run(() => updateDoc(doc(todoCollection(), todo.id), { title }))
  }
  function removeTodo(todo) {
    return run(() => deleteDoc(doc(todoCollection(), todo.id)))
  }
  return { todos, loading, busy, message, addTodo, toggleTodo, renameTodo, removeTodo }
}

A19 · onSnapshot으로 목록을 갱신

개념 정의

스냅샷은 특정 시점에 관찰한 쿼리 결과입니다.

실행 예시

다른 창에서 title 변경 → 새 스냅샷 → 목록 갱신

코드를 읽는 순서

관찰

초기 결과와 이후 변경을 받습니다.

변환

문서 데이터를 배열로 만들고 id를 붙입니다.

화면

setTodos가 새 목록을 렌더링합니다.

조금 더 자세히

item.data()는 문서 필드 객체, item.id는 문서 ID입니다. 펼침 문법 ...으로 필드를 옮긴 다음 id를 추가합니다. Effect의 [uid]가 바뀌면 이전 관찰을 정리하고 새 경로를 관찰합니다. 로그아웃으로 컴포넌트가 사라질 때도 정리합니다.

문법과 실행 과정을 자세히 읽기

snapshot.docs → 배열 변환

snapshot.docs는 조회된 문서 스냅샷들의 배열입니다. map이 각 문서를 순회하고 item.data()로 필드 객체를 읽습니다. item.id는 필드가 아니라 문서의 식별자이므로 따로 붙입니다.

({ ...item.data(), id: item.id })

...은 읽어 온 필드를 새 객체에 펼칩니다. 뒤에 id 속성을 추가해 수정·삭제 대상에 사용할 수 있게 합니다. 화살표 함수 바로 뒤의 ({ ... })는 객체를 반환한다는 뜻입니다. 괄호 없이 { ... }만 쓰면 함수 본문과 혼동할 수 있습니다.

저장 요청과 관찰 결과는 별개

addDoc은 쓰기 결과를 알려 주고 onSnapshot은 현재 목록을 알려 줍니다. 관찰은 로컬 변경을 서버 확정 전에 알릴 수도 있으므로 항상 저장 성공 다음에만 콜백이 온다고 가정하지 마세요. Effect의 [uid]가 바뀌면 이전 관찰을 해제한 뒤 새 계정 경로를 관찰합니다.

A23 · updateDoc과 deleteDoc의 차이

개념 정의

문서 참조는 컬렉션 경로와 문서 ID로 대상을 지정합니다.

실행 예시

done=false → 체크 → done=true · 삭제는 문서 제거

코드를 읽는 순서

updateDoc

deleteDoc

조금 더 자세히

updateDoc은 제공한 필드만 바꿉니다. renameTodo도 같은 문서의 title만 수정합니다. 문서가 없다면 updateDoc은 실패합니다. 화면에서는 확인 창을 거친 뒤 removeTodo를 호출합니다. 실제 삭제는 되돌리기 코드가 별도로 구현되어 있지 않습니다.

A29 · Rules에서 문서 주인 확인

개념 정의

Security Rules는 Firebase 서버가 각 데이터 요청의 허용 여부를 판단하는 규칙입니다.

실행 예시

A가 users/A/todos 읽기: 허용 · B가 같은 경로 읽기: 거부

코드를 읽는 순서

경로의 uid

/users/{uid}/todos/{todoId}에서 얻은 값

request.auth

로그인한 요청자의 인증 정보

isOwner

로그인한 UID와 경로 UID가 같아야 true

조금 더 자세히

브라우저에서 uid 문자열을 바꾸더라도 request.auth.uid는 임의 문자열이 아니라 인증된 요청 정보입니다. 화면에서 다른 계정의 목록을 숨기는 것과 서버가 접근을 거부하는 것은 서로 다른 단계입니다. 로그인하지 않은 요청은 request.auth가 null입니다.

문법과 실행 과정을 자세히 읽기

경로 변수 {uid}

중괄호는 실제 요청 경로에서 값을 받는 자리입니다. users/ABC/todos/t1 요청에서는 uid가 ABC이고 todoId가 t1입니다. JavaScript 템플릿 문법이 아니라 Rules의 경로 매칭 문법입니다.

request.auth != null && ...

&&는 두 조건을 모두 만족해야 참입니다. 먼저 인증 정보가 있는지 검사하고, 있을 때만 request.auth.uid를 경로의 uid와 비교합니다. 미로그인 요청은 앞 조건에서 거부됩니다.

read, delete에 적용되는 조건

이 샘플은 조회·삭제에는 isOwner를 요구합니다. 생성·수정에는 소유자 조건에 더해 데이터 형식과 변경 필드 조건을 요구합니다. 한 allow 줄이 모든 요청 종류를 허용하는 것은 아닙니다.

firestore.rules 전체 코드
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /users/{uid}/todos/{todoId} {
      function isOwner() {
        return request.auth != null && request.auth.uid == uid;
      }
      function validTodo() {
        let data = request.resource.data;
        return data.keys().hasAll(['title', 'done', 'createdAt'])
          && data.keys().hasOnly(['title', 'done', 'createdAt'])
          && data.title is string
          && data.title.size() > 0 && data.title.size() <= 80
          && data.title.matches('.*[^ ].*')
          && data.done is bool
          && data.createdAt is timestamp;
      }
      allow read, delete: if isOwner();
      allow create: if isOwner() && validTodo()
        && request.resource.data.done == false
        && request.resource.data.createdAt == request.time;
      allow update: if isOwner() && validTodo()
        && request.resource.data.diff(resource.data)
          .affectedKeys().hasOnly(['title', 'done']);
    }
  }
}

문법과 실행 과정을 자세히 읽기

hasAll은 title, done, createdAt이 모두 있는지 확인합니다. hasOnly는 그 세 필드 외의 필드가 없는지 확인합니다. 둘을 결합하면 필요한 필드가 정확히 존재하도록 제한할 수 있습니다.

형식과 내용은 별도 조건

title is string은 자료형 검사입니다. size() 범위와 matches는 내용 검사입니다. done에 문자열 "false"를 보내면 사람이 보기에는 비슷해도 bool 조건을 통과하지 못합니다.

현재 matches('.*[^ ].*')는 일반 공백 외의 문자가 적어도 하나 있는지 검사합니다. 모든 종류의 공백을 trim과 똑같이 처리한다는 뜻은 아닙니다. 브라우저 검사와 서버 Rules의 실제 조건을 각각 읽어야 합니다.

개념 정의

main에 새 커밋 push → Deploy to GitHub Pages 실행

코드를 읽는 순서

on

main push 또는 수동 실행으로 시작

permissions

concurrency

조금 더 자세히

YAML에서는 들여쓰기가 구조를 결정합니다. runs-on은 작업을 실행할 GitHub runner 환경이고 학생의 Ubuntu 서버 주소가 아닙니다. id-token: write는 배포 인증을 위한 토큰 발급 권한입니다. 이번 Ubuntu 배포는 별도로 직접 scp 업로드합니다.

문법과 실행 과정을 자세히 읽기

on과 jobs의 역할

on은 언제 시작할지, jobs는 무엇을 실행할지 정의합니다. main에 push하거나 Actions에서 수동 실행하면 workflow가 시작됩니다. YAML은 들여쓰기로 소속을 나타내므로 복사할 때 공백을 유지하세요.

권한의 범위

contents: read는 코드 읽기, pages: write는 Pages 게시, id-token: write는 배포 인증 토큰 발급을 위한 권한입니다. 여기의 write는 학생 Ubuntu 계정의 파일 쓰기 권한과 관계없습니다.

concurrency와 최신 실행

같은 pages 그룹에 새 실행이 들어오면 cancel-in-progress 설정으로 이전 실행을 취소합니다. 이전 커밋의 오래된 배포 작업이 계속 진행되는 상황을 줄입니다. GitHub Actions 실행 번호와 커밋을 함께 확인하세요.

    branches: [main]
  workflow_dispatch:
permissions:
  contents: read
  pages: write
  id-token: write
concurrency:
  group: pages
  cancel-in-progress: true

  deploy:

    environment:

      VITE_FIREBASE_AUTH_DOMAIN: ${{ secrets.VITE_FIREBASE_AUTH_DOMAIN }}

개념 정의

웹 서버는 HTTP 요청을 받아 파일이나 처리 결과를 응답하는 프로그램입니다.

실행 예시

코드를 읽는 순서

HTTP 요청을 받을 포트

index

조금 더 자세히

로컬의 dist 안에 있는 내용이 /var/www/mini-todo 안에 놓여야 합니다. dist 폴더 자체를 한 겹 더 넣으면 root 바로 아래에 index.html이 없어집니다. server_name _와 default_server 조합은 수업용 단일 사이트 VM의 기본 요청 처리 설정입니다.

문법과 실행 과정을 자세히 읽기

listen과 server_name

listen 80은 HTTP 80번 포트를 수신합니다. default_server는 해당 주소·포트에서 이름이 매칭되지 않은 요청의 기본 서버를 지정합니다. server_name _ 자체가 모든 이름을 매칭하는 특별한 와일드카드는 아닙니다.

root와 index를 조합

root /var/www/mini-todo에 URI를 이어 실제 파일을 찾습니다. / 요청에는 index index.html 설정을 사용합니다. 따라서 /var/www/mini-todo/index.html이 있어야 합니다. /var/www/mini-todo/dist/index.html이면 한 겹 깊게 올린 것입니다.

설정 파일 반영

설정 파일을 수정한 것만으로 실행 중인 Nginx 설정이 바뀌지는 않습니다. sudo nginx -t로 문법과 참조 파일을 점검하고 성공한 뒤 sudo systemctl reload nginx로 반영합니다. nginx -t가 성공해도 웹 파일의 배치까지 검증한 것은 아닙니다.

참고: Nginx root·try_files 문서 · Cache-Control의 no-cache 의미

A40 · try_files로 파일과 화면 경로 처리

개념 정의

try_files는 요청 경로에 해당하는 파일·폴더를 순서대로 검사합니다.

실행 예시

새로고침

브라우저의 화면 경로 요청에도 앱 HTML 제공

조금 더 자세히

SPA는 하나의 HTML에서 화면을 바꾸는 앱입니다. 이 샘플은 별도의 화면 라우터를 사용하지 않지만 설정은 HTML fallback을 준비합니다. /assets/까지 무조건 index.html을 주면 누락된 JS 요청에 HTML이 반환되어 원인 파악이 어려워집니다. nginx -t 성공 후 reload합니다.

문법과 실행 과정을 자세히 읽기

$uri와 =404

$uri는 Nginx가 처리하는 요청 URI입니다. /assets/ 위치의 try_files $uri =404는 해당 파일이 있으면 제공하고 없으면 404로 끝냅니다. 이 문자열은 셸 변수가 아니므로 설정 파일에 $uri 그대로 남아야 합니다.

$uri/와 /index.html

일반 location은 파일, 디렉터리를 차례로 확인하고 없으면 /index.html로 내부 전환합니다. 브라우저의 앱 경로를 새로고침해도 HTML을 받을 수 있게 하는 설정입니다. 실제 화면 경로 처리는 앱 라우터가 구현해야 합니다.

no-cache의 의미

Cache-Control: no-cache는 저장 자체를 무조건 금지한다는 뜻이 아니라, 재사용 전에 서버에 유효성을 확인하도록 요구합니다. 이 설정에서는 일반 location 응답에 적용합니다. 자원이 없는데 HTML을 JS 대신 돌려주는 문제와는 구분하세요.

조금 더 자세히

실행 흐름을 읽을 때 함수 이름으로 파일을 따라갑니다. addTodo는 생성 요청, onSnapshot은 관찰 결과의 반영을 맡습니다. 입력이 사라지는 조건과 목록이 갱신되는 경로를 구분하면 비동기 실행을 이해하기 쉽습니다.

입력값부터 함수 따라가기

TodoPanel의 title이 addTodo(title)의 인자가 되고 cleanTitle을 거쳐 addDoc의 title 필드가 됩니다. 같은 title이라는 단어도 화면 상태, 함수 지역 변수, 저장 필드라는 서로 다른 위치에서 사용됩니다.

두 결과 경로

run의 반환값은 입력창을 지울지 결정합니다. onSnapshot 콜백은 목록에 무엇을 보여 줄지 결정합니다. 쓰기 응답과 관찰 알림의 순서를 하나로 고정하지 않고 각자의 역할로 이해하세요.

실패 지점부터 확인하기

입력 검사에서 false라면 DB 요청 전입니다. permission-denied라면 서버 Rules가 거부했습니다. 저장은 됐는데 목록이 비어 있다면 조회 경로·정렬 필드·관찰 오류를 확인합니다. 증상마다 확인할 파일이 다릅니다.
